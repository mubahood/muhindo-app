# muhindo-app — Public Site Plan v2: e‑Learning & Client Onboarding

**Agent guide for the logged-out experience.** The previous two documents covered the
inside of the platform (`PROJECT_PLAN.md` built it, `LMS_MASTER_PLAN.md` masters the
logged-in learning experience). This one covers everything a **stranger** sees:
landing page, the e‑Learning catalogue, course pages, registration, checkout, and the
"start a project" client funnel. The goal is a public site that is stable, fast,
findable on Google, and — above all — reads like it was written by a real teacher and
builder, not generated by a machine.

Authority order when documents conflict: this file → `LMS_MASTER_PLAN.md` →
`PROJECT_PLAN.md` (historical).

**v2 note:** this is a rewrite of the original plan, done from *inside* the codebase
after LMS P0–P5 and the portfolio redesign were both built. It keeps v1's structure,
voice, and every requested capability, corrects facts that were guessed or already out
of date, resolves open questions into firm decisions, and tightens W0–W7 into gated
steps. See "Verified current state" at the end for what changed and why, and
`PUBLIC_BUILD_LOG.md` for the full change list.

## 1. Voice & positioning (the "human-created" requirement)

### 1.1 The problem with the current landing wording

The landing currently frames Muhindo as someone who builds enterprise systems for
clients — full stop. That framing quietly tells students "this site is not for you"
and tells small customers "you're too small." Rewrite the positioning so the site
leads with **two open doors**:

- **Learn with me** — I teach computer programming and computer-related courses,
  online, practically, in plain language.
- **Build with me** — I design and build software for anyone with a real problem:
  individuals, startups, schools, clinics, NGOs, government teams, and yes,
  enterprises. Never say "I only do enterprise projects" or "I only work with
  clients." The word is **"you"** — "have an idea? let's build it."

### 1.2 Writing rules (apply to every public page)

- First person, warm, direct. "I teach…", "I built…", "You'll learn…". Muhindo is a
  person, not a corporation — the site must sound like him.
- Short sentences. Concrete claims with numbers where true (years, projects shipped,
  students taught) — pull real facts from the portfolio content/seeder; **never invent
  numbers, testimonials, student counts, or reviews.** If a number isn't real yet,
  don't display the widget. Real numbers already live and available: "23,000+
  subscribers, 200+ tutorials" (courses header), "9+ years", "20+ systems shipped"
  (home stat row) — reuse these, keep them sourced from settings, don't restate them
  from memory in new copy.
- No AI-boilerplate phrases: ban "unlock your potential", "cutting-edge", "seamless",
  "empower", "world-class", "take your skills to the next level". Say what the course
  actually teaches instead.
- Uganda-aware, world-open: prices show clearly in UGX (or the course currency),
  mobile money named explicitly (MTN MoMo, Airtel Money) — these are trust signals
  locally; English copy plain enough for everyone.
- Every page passes the read-aloud test: if a sentence would sound odd said to a
  student's face, rewrite it.

### 1.3 Landing page (`/`) — add the missing e‑Learning strip

The portfolio redesign (`PORTFOLIO_REDESIGN_PLAN.md`, now committed) already produced a
lean home: hero, a compact "what I do" icon row, 3 featured projects, one closing CTA
band. It is genuinely lean now — but it has **zero mention of courses**. That's the one
real gap this section closes; it is not a rebuild. New section order for `/`:

1. **Hero** — keep the redesigned hero, reword per §1.1: name, one-line identity
   ("Software engineer & programming teacher"), two CTAs side by side: `Explore
   e‑Learning` (gold, primary) and `Start a project`. One real photo. No sliders, no
   particles. (Currently one CTA — "Get in touch" — needs the second added and the
   headline reworded away from "enterprise systems … for Africa" per the live-audit
   finding below.)
2. **e‑Learning strip (new)** — "I train computer programming and computer-related
   courses" + up to 3 featured published course cards + "Browse all courses →". Insert
   this immediately after the hero, above the existing "what I do" icon row — courses
   must not be invisible on the landing page.
3. **Build-with-me strip** — existing icon row, reworded per §1.1, CTA to
   `/start-a-project` added alongside the existing `/services` link.
4. **Selected work** — existing (unchanged).
5. **Contact** — existing form + CTA band (unchanged).

No new schema. This is copy + one new partial (`portfolio/partials/elearning-strip.blade.php`,
reusing `.grid`/`.proj-card`, styled like the existing "Recent projects" grid) on an
already-existing route.

## 2. e‑Learning: the public catalogue re-imagined

### 2.1 Naming & routes — decision

Public name everywhere: **e‑Learning** (nav item, page titles, footer). Internal code
keeps `Course*` naming — no backend churn.

Routes: `/e-learning` (listing) and `/e-learning/{course:slug}` (detail) become
canonical. `/courses` and `/courses/{slug}` become **301 redirects** to them (defined
as plain `Route::redirect(...)`, permanent: true — not a controller branch, so there's
no risk of the old routes silently staying "live"). Preview/enroll/checkout routes
move under the new prefix too (`/e-learning/{slug}/preview/{lesson}`, `/enroll`,
`/checkout`) with the same 301 treatment for their old paths, since a mid-checkout
bookmark or an already-sent email link must keep working. Nav: `e‑Learning` sits first
after Home in `layouts/marketing.blade.php`'s nav (currently `Work · About · Skills ·
Courses · Contact`), visually accented (small gold dot).

### 2.2 Listing page `/e-learning` (Udemy-inspired, one-instructor scale)

Header block: title "e‑Learning", one positioning paragraph ("I teach computer
programming and computer-related courses — practical, project-based, in plain
English. Learn at your pace, get a verifiable certificate."), and honest trust chips
derived from live data only: `N courses · N lessons · certificate on completion ·
pay with MTN MoMo, Airtel Money or card`.

The grid: responsive course cards (1 col mobile → 2 → 3 ≥1024px), each card:

- Cover image (fixed 16:9, lazy-loaded, sized to prevent layout shift; branded
  navy/gold placeholder when missing)
- Category chip + level chip (Beginner/Intermediate/Advanced)
- Title (max 2 lines, ellipsis) + one-line hook — needs a new `courses.tagline`
  varchar(160) column (nullable; fall back to `Str::limit(description, 80)` when
  blank so existing rows degrade gracefully instead of showing empty space)
- Meta row: lesson count (`lessonCount()`, already exists) · total duration (sum of
  `lessons.duration_minutes`, needs a subquery — no column exists for this today) ·
  ⭐ rating (`reviews_count`/`reviews_avg_rating` — **already wired** via
  `withCount`/`withAvg` in `CourseCatalogueController::index`; the existing blade
  already guards it behind `@if($course->reviews_count > 0)`, keep that guard)
- Price row: **Free** badge (gold) or `UGX 150,000` formatted. Drop the "sitewide
  promo coupon" struck-through display from v1 — coupons in this codebase are applied
  per-redemption at enrollment time (§5.1), not as a sitewide always-on discount; a
  card-level strike-through would show a price the visitor can't actually get without
  a code. Show it only on the detail page's buy box, and only after a coupon is
  actually applied.
- Whole card clickable; hover lift consistent with the design system

Controls (server-rendered, URL-driven — `?category=&level=&price=&sort=&q=` — so
filtered pages are shareable and crawlable; enhance with Alpine/AJAX later, never
require JS):

- Filter: category (from distinct published categories), level, price (Free/Paid)
- Sort: Newest · Price low→high · Most enrolled
- Search box over title/description (simple `LIKE` is fine at this scale)
- Empty state: friendly line + "clear filters" + contact link ("want me to teach
  something specific? tell me")

Pagination past 9 courses; eager-load counts (`withCount('lessons')`, sum durations
via subquery) — zero N+1 on this page.

### 2.3 Course detail `/e-learning/{slug}` (the sales page)

Two-column ≥1024px, single column mobile (buy box becomes a sticky bottom bar with
price + CTA — Udemy's mobile pattern):

**Main column:**
1. Breadcrumb (e‑Learning / Category / Title) — also JSON-LD BreadcrumbList
2. Title, tagline, meta chips (level, duration, lesson count, language, last updated
   from `updated_at`)
3. **What you'll learn** — 4–8 outcome bullets — needs a new `courses.outcomes` JSON
   column, editable in the admin form as a one-per-line textarea (cast `array`,
   `null` when empty — section hidden, not shown empty)
4. **Curriculum accordion** — modules with lesson rows (title, duration); already
   built server-side (`courses/show.blade.php` renders `$course->modules.lessons`
   today, just not as an accordion). `is_free_preview` lessons already get a **Free
   preview** tag linking to the working guest preview route
   (`courses.preview` → `CourseCatalogueController::preview`, enforces
   `is_published`/`is_free_preview`, already built — nothing to build here, just
   restyle as an accordion and carry the route rename from §2.1)
5. **Requirements** — needs a new `courses.requirements` JSON column, same editing
   pattern as outcomes
6. **Description** — rich text (already rendered; `MarkdownRenderer` already used
   elsewhere in this controller for lesson content — reuse it here for consistency)
7. **Your instructor** — photo, bio pulled from portfolio settings, real stats only
8. **Reviews** — already conditionally rendered (`$publishedReviews`, built); carry

9. **FAQ** — one shared FAQ (how do I pay, is it self-paced, do I get a certificate,

**Buy box (sticky right / bottom bar mobile):** cover thumb, price (or Free),
`Enroll now` / `Buy course` CTA, "includes" list (N lessons, X hours, certificate of
completion, learn at your pace — drop "downloadable materials," nothing in the data
model represents that today and it must not be promised), payment-method icons (MTN
MoMo, Airtel Money, Visa/Mastercard — Flutterwave's hosted page already supports all
of these via `payment_options=card,mobilemoneyuganda,banktransfer,ussd`, confirmed in
`config/services.php`, no gateway work needed), a coupon field (this is where coupon
entry moves to — see §5.1 for why), and a money-comfort line ("Secure payment via

Also needs a `courses.cover_alt` string column (nullable, fallback to the course

### 2.4 Make e‑Learning stand out sitewide

Footer column "e‑Learning" listing top course links (internal linking = SEO), a
courses strip on portfolio project pages ("I also teach — see how I build things
like this"), and the `Explore e‑Learning` CTA in the hero (§1.3). One tasteful
accent-animation on the landing course cards; nothing that moves on scroll-jack.

### 2.5 Demo content — build a real public catalogue, not lorem text

The database currently has exactly one course: a bare `CourseFactory` row
("Accusantium perferendis ut.", lorem description, zero modules, zero lessons — this
is what renders on `/courses` today). A separate `DemoCourseSeeder` exists but is
explicitly dev-scoped ("Laravel Fundamentals (**Demo**)", one free course, one module)
and not what a public catalogue should show.

Write a new `PublicCourseCatalogueSeeder` (opt-in, `--class=`, not wired into
`DatabaseSeeder`'s default chain — same convention as `DemoCourseSeeder`) that creates
**6–8 real-looking courses** spanning what Muhindo actually teaches (web development,
mobile development, databases, one free "starter" course, a couple of paid ones with
real UGX prices), each with a real title, tagline, 2–3 modules with several lessons
each (durations set, at least one `is_free_preview` lesson per course so §2.3's preview
flow has something to show), outcomes, requirements, and a category/level spread wide
enough to exercise §2.2's filters. This seeder is what every W2 page gets built and
reviewed against — never lorem text.

## 3. New-student registration & onboarding (simple and straightforward)

### 3.1 Principle

A stranger should get from "found a course" to "watching lesson 1" in **under two
minutes for a free course**, and in one continuous flow for a paid one. Registration
is never a dead end; it always continues what the person was doing.

### 3.2 Flows (implement exactly)

**A. Free course, guest:** course page → `Enroll now` → register-or-login screen
*with course context shown* (cover + "to start {course}") → after auth: enrollment
created → redirect **straight into lesson 1** (not the dashboard). Toast: "You're
in — lesson 1 is starting."

**B. Paid course, guest:** course page → `Buy course` → same contextual auth step →
checkout (§5) → payment confirmed → redirect into lesson 1 + receipt email.

**C. Already-authenticated:** one click from course page to enrolled/checkout —
never re-ask what we know.

**Implementation (none of this exists yet — `StudentRegistrationController::store`
unconditionally redirects to `route('dashboard')` today, with no course context
carried at all):** register/login accept an `intended_course` signed query param;
`register()`/`login()` GET handlers pass it through to the view as a hidden field;
`StudentRegistrationController::store` (and the existing login controller) read it
after auth and, if present, call the same enroll logic `CourseCatalogueController::enroll`
uses instead of redirecting to the dashboard. Social auth is out of scope (keep it
simple); email+password only.

### 3.3 Registration form — minimum fields

Name, email, password (with visibility toggle), one checkbox for terms — the terms
checkbox is the only addition needed; name/email/password already match this exactly.
Nothing else — no phone, district, or profile questions at signup (profile drawer
exists for later; ask for the phone number only at mobile-money checkout, where
Flutterwave's own hosted page already collects it — no separate phone field needed on
our side at all). Client accounts remain admin-created only (per `PROJECT_PLAN.md` §7,
confirmed still true — `Admin\ClientController::store` is the only place a `Client`
row is created) — the public register page is for students and says so ("Creating an
account to hire me for a project? Use Start a project instead →").

Email verification: send the existing verification mail but **do not block learning**
on it for free courses; nag-banner in the app until verified, hard-require
verification before a certificate is issued (ties into `LMS_MASTER_PLAN.md` §4.6).

### 3.4 First-session onboarding (post-registration)

- Welcome email (extend the existing mail templates): what you enrolled in, link to
  continue, what to expect, how to ask questions.
- First-visit checklist card on the student dashboard (dismissible, stored per user):
  ✓ verify email · ▶ start your first lesson · ⚙ complete your profile. Three items
  max — this is onboarding, not homework.
- Empty states everywhere a new student can land (`/learn` with one enrollment,
  dashboard) point to the next action, never to a blank screen.

## 5. Checkout: pay with mobile money or card, with coupons

Reuse the running machinery — `Invoice`/`InvoiceItem`/`Payment`,
`BillingService`, `CouponService`, `FlutterwaveGateway`,
`Admin\GatewayPaymentController` (handles both the redirect-start and the
callback/webhook, already idempotent via `gateway_logs` dedup — confirmed in code, not
assumed). **All of this already exists and is exercised by course checkout today** —
`CourseCatalogueController::enroll` already calls `BillingService::generateCourseInvoice`
for paid courses, `courses.checkout` already shows the resulting invoice, and
`GatewayPaymentController::start`/`callback`/`webhook` already drive it to completion.
This section is a UI rebuild on top of proven machinery, not new payment logic.

### 5.1 How coupons actually work here (v1 got this wrong — firm decision)

v1 imagined a checkout-page coupon field with a separate "AJAX validate" endpoint that
recomputes a total before payment. That does not match how `CouponService::redeem()`
is built: a code is validated and its use **atomically consumed** (`used_count`
incremented, race-safe via `lockForUpdate`) the moment an invoice is generated — not
at payment time. `CourseCatalogueController::enroll` already takes an optional
`coupon_code` and passes it straight into `generateCourseInvoice`, which calls
`redeem()` before the invoice is created.

Decision: **keep this architecture — it's simpler and already correct** (no
"reserve now, confirm later" state to manage, no risk of a coupon being validated but
never actually consumed). Move the coupon input from its current plain `<input>` on
the course-show enroll form into the **buy box** on the redesigned detail page (§2.3)
so it reads as part of "buying," not a stray text field — but it still submits through
the existing `courses.enroll` POST, still redeems before the invoice exists. Do **not**
build a separate validate-then-redirect endpoint; it would duplicate `redeem()`'s
locking logic for no behavioral gain. The checkout page itself then simply **displays**
the already-computed result: `$invoice->items` for the course line (`subtotal`),
`$invoice->discount`, `$invoice->total` — all three columns already exist on
`Invoice` — so "struck-through original + discounted total" is a template change, not
a new query.

### 5.2 Checkout page rebuild `/e-learning/{slug}/checkout` (auth required)

Current state: extends `layouts.app` (correct — it's a post-login page, keep it there,
not `layouts.marketing`), shows only the course name, invoice total, and a single "Pay
with Flutterwave" button posting to the existing generic `invoice.pay` route. Rebuild
the page (same route, same controller action, richer view) with:

- Order summary: course cover thumb, title, `subtotal` line, `discount` line (only
  when > 0, with the coupon code that earned it), `total` — all read straight off the
  already-loaded `$invoice`.
- Payment-method reassurance row (MTN MoMo / Airtel Money / Visa / Mastercard icons) —
  informational only; Flutterwave's hosted page (opened by the existing "Pay" button)
  already lets the payer choose among `card,mobilemoneyuganda,banktransfer,ussd`
  (confirmed default in `config/services.php`), so no method-selection UI is needed on
  our side to make mobile money or cards work — both already work today.
- Failure/timeout path: the callback route already redirects back with a friendly
  message on a failed/cancelled Flutterwave attempt (verify this in W4, extend the copy
  if terse) — enrollment stays `pending`, invoice reusable, never a white error page,
  never a double charge (webhook dedup already guards this — write a replay test, don't
  rebuild the guard).
- Free courses **never** touch checkout — direct enroll (existing flow, unchanged).

**Deferred (optional, real UX gain but not required for the core loop):** passing a
`payment_options` hint per-request so Flutterwave's hosted page opens pre-selected on
the tab matching what the buyer picked on our page. `DEFERRED` — the current sitewide
default already exposes every method the plan asks for; pre-selection saves the payer
one tap. Build only if W4 finishes early.

## 7. Responsiveness & stability

- Mobile-first: every new template designed at 360px first, then enhanced at 768 /
  1024 / 1280. Test points: 360, 390, 768, 1024, 1440. The buy box → sticky bottom
  bar behaviour (§2.3) is the flagship mobile pattern; tap targets ≥ 44px.
- Server-rendered Blade everywhere; JS (Alpine/axios, plus `wire:navigate` already
  wired across the whole public site — committed) only *enhances* (accordion,
  filters-without-reload). Every feature works with JS disabled — `wire:navigate` is a
  progressive enhancement over real `<a href>`s, already verified safe for SEO in the
  portfolio redesign; new pages just need real URLs, same as existing ones.
- Stability: all public queries eager-loaded and paginated; listing cached
  (invalidate on course save); rate-limit contact, register, project-inquiry, and
  enroll/coupon-redeem endpoints (the enroll route already has `throttle:10,1` —
  extend the same treatment to the new inquiry endpoint); replace the auth pages'
  inherited medical `doodle-bg` partial (§ verified below) with a code/learning-themed
  pattern or a plain brand surface; branded 404/500 pages (Laravel's default is live
  today — verified below) with a human line ("that page wandered off — browse courses
  instead?") and a link back to `/e-learning`; feature tests for every public route
  (guest + auth variants), redirects, checkout happy path + webhook replay, coupon edge
  cases (expired, exhausted, wrong course — `CouponService`'s exceptions already cover
  these, write tests that exercise each one through the HTTP layer, not just the
  service), and inquiry submission.
